# Отрисовка строк

Что приходит в `renderItem`, как выбирать ключи и типы, откуда берутся размеры
и как хранить состояние внутри ячейки.

## Что приходит в `renderItem`

```ts
interface IAnchorListRenderItemProps<TItem> {
  item: TItem;
  index: number;
  itemKey: string;
  type: string;
  extraData: unknown;
  stickyOffset?: SharedValue<number>;
  stickyPinned?: SharedValue<boolean>;
}
```

```tsx
const renderItem = useCallback(
  ({ item, index }: IAnchorListRenderItemProps<IMessage>) => (
    <MessageRow message={item} isFirst={index === 0} />
  ),
  [],
);
```

`index` — индекс в **текущих** данных: после подгрузки страницы сверху у того же
сообщения он другой. Всё, что должно пережить смену данных, адресуется ключом —
он приходит полем `itemKey`. Последние два поля нужны только прилипанию в режиме
`offset`, см. [Прилипание](sticky.md#режим-offset).

Функцию мемоизируйте: она уходит в каждый смонтированный контейнер, и новая
ссылка перерисовывает их все.

## Ключи

На ключе держатся измеренные размеры, привязка контейнеров, опоры удержания
позиции, `scrollToKey` и `getPositionByKey`. Ключ должен быть постоянным для
элемента, уникальным и не зависеть от индекса:

```tsx
keyExtractor={message => message.id}                        // да
keyExtractor={row => `${row.type}:${row.id}`}               // да, если id уникален внутри типа
keyExtractor={(_, index) => String(index)}                  // нет
keyExtractor={message => `${message.id}:${message.status}`} // нет: ключ меняется у того же элемента
```

Ключ, меняющийся вместе с элементом, для списка означает, что один элемент
исчез и появился другой: измеренная высота теряется, удержание позиции остаётся
без опоры.

## Типы строк

`getItemType` говорит, какие строки похожи друг на друга:

```tsx
getItemType={row => {
  if (row.type !== "message") return row.type;

  return row.hasAttachment ? "message-media" : "message-text";
}}
```

Тип влияет на две вещи:

1. **Переработку контейнеров.** Свободный контейнер того же типа уже держит
   нужное поддерево, поэтому React меняет пропы вместо перемонтирования.
2. **Оценку неизмеренных строк.** Средний размер копится отдельно по каждому
   типу, и новая строка получает среднее своего типа, а не общее.

Строки заметно разной высоты разводите по разным типам, иначе среднее будет
врать обоим.

## Размеры

Размер строки — её протяжённость вдоль оси скролла: высота в вертикальном
списке, ширина при [`horizontal`](props.md#horizontal-boolean). Поперёк оси
строка растянута на весь вьюпорт, задавать это самому не нужно.

Три источника размера, в порядке приоритета:

| Источник | Когда используется |
| --- | --- |
| `getFixedItemSize` | Размер объявлен — измерение пропускается |
| Измеренный размер | Строка была смонтирована и измерена |
| Оценка | Средний замер по типу; до первых замеров — `estimatedItemSize` |

### Объявленные размеры

```tsx
const rowHeight = (row: ChatRow): number | undefined => {
  if (row.type === "day") return 44;
  if (row.type === "spinner") return 56;

  return undefined; // сообщение — измеряем
};

<AnchorList getFixedItemSize={rowHeight} estimatedItemSize={92} />;
```

Возврат `undefined` означает «неизвестно, измеряй». Список отводит ровно
столько, сколько объявлено, и не проверяет: если строка на самом деле выше,
соседи налезут друг на друга. Объявленный размер обязан включать отступы,
границы и `ItemSeparatorComponent`.

Объявленный размер обратно в измеряемый не превращается. Перевести список с
объявленных размеров на измеряемые можно только сменой `key`:

```tsx
<AnchorList key={knownHeights ? "fixed" : "measured"} ... />
```

### Измеряемые размеры

Строка без объявленного размера измеряется при монтировании, до этого ей
отводится оценка. Новая строка, появившаяся в данных, не занимает места, пока
не измерена, поэтому раскладка не прыгает дважды: сначала на оценку, потом на
факт. Если разом появилось больше 32 строк, они встают по оценке без ожидания.

Список показывается, когда видимые строки измерены или объявлены. Если задан
`initialScroll`, показом распоряжается
[стартовая позиция](scrolling.md#стартовая-позиция).

Как измерение устроено внутри — [Механика](mechanics.md#4-что-происходит-когда-строка-измерилась).

### Кэш измерений

Измеренные размеры живут в списке и умирают вместе с ним: ушёл с экрана и
вернулся — строки меряются заново, а стартовая позиция доводится по оценкам
несколько кадров. [`sizeCache`](props.md#sizecache-anchorlistsizecache) выносит
размеры наружу:

```tsx
import { createAnchorListSizeCache } from "@epifanovmd/anchor-list";

// Модуль экрана: кэш переживает и размонтирование, и навигацию.
const sizeCache = createAnchorListSizeCache();

export const ChatScreen = () => (
  <AnchorList sizeCache={sizeCache} keyExtractor={row => row.key} ... />
);
```

Кэш адресован ключом, поэтому переживает подгрузку истории и перезагрузку
данных. Список пишет в него каждый замер и читает при монтировании: строки, что
окажутся на экране, известны заранее — `readyToRender` наступает с первого
кадра, `initialScroll` по ключу встаёт с первой попытки. В связке со снимком
[`getScrollAnchor`](imperative-api.md#getscrollanchor) это «открыть переписку
ровно там, где закрыл, без единого лишнего кадра».

| Что | Как |
| --- | --- |
| Предзаполнить | `sizeCache.set(key, size)` — например размерами с сервера |
| Очистить | `sizeCache.clear()` — при смене ширины экрана или масштаба шрифта |
| Забыть строку | `sizeCache.delete(key)` |
| Сколько в кэше | `sizeCache.size` |

Устаревший размер не ломает раскладку: строка рисуется, узел приходит с другой
геометрией, и свежий замер заменяет кэш как обычный рост или сжатие — с
компенсацией позиции, если включён `maintainVisibleContentPosition.size`. До
замера строка занимает место по кэшу. Средний размер по типу из кэша не
восстанавливается: он копится из свежих замеров, и строки вне кэша до первых
замеров оцениваются `estimatedItemSize`.

Кэш растёт с каждым новым ключом и сам ничего не забывает — размер записи
десятки байт, и переписка на сто тысяч сообщений стоит единицы мегабайт. Если
это дорого, чистите его при уходе с экрана.

## Переработка контейнеров

```tsx
<AnchorList recycleItems getItemType={row => row.type} />
```

Контейнер и без этого пропа переживает смену строки, но поддерево ячейки внутри
него пересоздаётся: старая строка размонтируется, новая монтируется. С
`recycleItems` поддерево остаётся, и React меняет ему пропы — при условии, что у
строк один тип. На однотипных строках это самая заметная экономия.

### Состояние внутри ячейки

> [!WARNING]
> **`useState` внутри перерабатываемой строки достаётся чужому элементу.** Он
> живёт вместе с контейнером, а контейнер при `recycleItems` меняет элементы под
> собой: развёрнутый текст, начатое проигрывание, снятая отметка, позиция
> карусели остаются от предыдущей строки.

Выбор зависит от того, обязано ли состояние пережить уход строки за пределы
буфера.

**Состояние живёт, пока строка на экране** — `useAnchorListItemState`. Хук
адресован ключом элемента и сбрасывается при смене ключа прямо в рендере:

```tsx
import { useAnchorListItemState } from "@epifanovmd/anchor-list";

const Row = ({ item }) => {
  // сбрасывается сам, когда контейнер возьмёт другой элемент
  const [expanded, setExpanded] = useAnchorListItemState(false);

  return <Pressable onPress={() => setExpanded(v => !v)}>{/* ... */}</Pressable>;
};
```

Начальное значение можно вычислить от элемента — при смене элемента оно
пересчитается:

```tsx
const [expanded, setExpanded] = useAnchorListItemState(() => item.expandedByDefault);
```

Хук вызывается **внутри компонента, который вернул `renderItem`**, а не в теле
самого `renderItem`. Неправильный вызов падает с объясняющей ошибкой.

**Состояние обязано пережить возврат к строке** — внешний стор по ключу
элемента:

```tsx
const renderItem = useCallback(
  ({ item, itemKey }) => (
    <Row
      item={item}
      expanded={expandedIds.has(itemKey)}
      onToggle={() => toggle(itemKey)}
    />
  ),
  [expandedIds, toggle],
);
```

## Пропуск повторных рендеров

По умолчанию элементы сравниваются по ссылке: строка перерисовывается, когда у
неё новый объект. Если данные пересобираются целиком на каждое изменение,
задайте своё сравнение:

```tsx
const itemsAreEqual = useCallback(
  (prev: IMessage, next: IMessage) =>
    prev.id === next.id &&
    prev.text === next.text &&
    prev.status === next.status,
  [],
);

<AnchorList itemsAreEqual={itemsAreEqual} />;
```

## Слоты

### Шапка и подвал

```tsx
<AnchorList
  ListHeaderComponent={<ChannelHeader channel={channel} />}
  ListFooterComponent={<TypingIndicator chatId={chatId} />}
/>
```

Принимаются элементом и типом компонента. Оба измеряются и входят в полную
высоту контента.

### Пустое состояние

```tsx
<AnchorList ListEmptyComponent={<EmptyChat />} />
```

Показывается вместо элементов, когда `data` пуст. Шапка и подвал остаются.

### Разделитель

```tsx
<AnchorList ItemSeparatorComponent={Divider} />
```

Разделитель рисуется **внутри** ячейки, следом за содержимым, и входит в её
размер. В `FlatList` это отдельный узел между ячейками, здесь — нет. Объявленный
через `getFixedItemSize` размер обязан включать разделитель.
