# Ведение библиотеки

Короткий свод: как я вношу правку, как её описываю и как выпускаю версию.
Настройка окружения и порядок работы с PR — в [CONTRIBUTING.md](../CONTRIBUTING.md).

---

## Цикл одной правки

**1. Баг сначала воспроизводится тестом.** Падающим — на текущем коде. Без этого
шага нельзя быть уверенным, что чинится причина, а не совпадение.

**2. Тест проверяется на регрессию.** Временно вернуть старый код и убедиться,
что тест падает. Тест, который проходит и до, и после, не защищает ни от чего.

**3. Починить и прогнать всё.**

```sh
yarn check     # линт + типы + тесты, то же гоняет CI
```

**4. Обновить документацию, если менялся публичный API.** Профильный раздел плюс
[props.md](props.md) — там перечислены все пропы и значения по умолчанию.

**5. Проверить на устройстве**, если правка про отрисовку, скролл или
компенсацию позиции. Тесты ядра этого не видят — см. ниже.

Если причину найти не удаётся, гадать в коде нельзя. Включить нужный канал
диагностики (`setAnchorListDebug("mvcp")` — все каналы перечислены в
[debugging.md](debugging.md)) или замер (`useAnchorListPerf`), снять лог с
устройства и разбирать по числам — см. [troubleshooting.md](troubleshooting.md).

## Коммиты

Формат обязателен, его проверяет `commitlint` на хуке `commit-msg`:

```
тип(область): что изменилось
```

### Типы

| Тип | Версия | В чендж-логе |
| --- | --- | --- |
| `fix` | патч | **Bug Fixes** |
| `feat` | минор | **Features** |
| `perf` | патч | **Performance Improvements** |
| `revert` | патч | **Reverts** |
| `refactor`, `docs`, `test`, `chore`, `ci`, `build`, `style` | нет | не попадает |

Тип решает не только номер версии, но и видимость. Починка, о которой стоит
знать снаружи, обязана быть `fix`, даже если по коду это выглядело как
перекладывание. И наоборот: правка внутренностей, ничего не меняющая в
поведении, — `refactor`, иначе чендж-лог заполнится строками, которые снаружи
ничего не значат.

### Заголовок

**Заголовок коммита — это готовая строка чендж-лога.** Ни тело, ни комментарии
туда не попадают. Значит писать надо не «что сделано с кодом», а «что изменилось
для того, кто ставит пакет».

```
плохо:  fix: поправил расчёт в sticky-offset
хорошо: fix(sticky): якорь вставал ниже кромки на высоту шапки
```

Первое читателю бесполезно — он не знает внутренних имён и не поймёт, чинит ли
это его симптом. Второе описывает то, что он видел на экране.

### Область

Группирует строки и показывает затронутую механику. Держаться одного набора имён,
совпадающего с каталогами `src/core`: `sticky`, `mvcp`, `edges`, `layout`,
`scroll`, `viewability`, `perf`.

### Одно изменение — один коммит

Каждый `fix` и `feat` даёт ровно одну строку. Пять правок в одном коммите
превратятся в одну строку, которая опишет только первую.

### Ломающее изменение

Отдельной строкой в теле — это самая ценная часть чендж-лога, сюда смотрит тот,
у кого после обновления перестало собираться:

```
feat(sticky): наборы прилипания вместо индексов

BREAKING CHANGE: `stickyIndices` заменён на `sticky` — массив наборов
с кромкой, режимом и отступом. Таблица соответствия в docs/sticky.md.
```

Одного слова «переименовано» мало: нужно, что делать.

**Пока мажор нулевой**, `BREAKING CHANGE` всё равно даёт лишь минор — так устроен
semver до `1.0.0`. Чтобы ломающие изменения поднимали мажор, надо выйти на
единицу.

### Хуки

На `pre-commit` идут линт, типы и тесты по изменённым файлам; на `commit-msg` —
проверка формата. Обходить их (`--no-verify`) не нужно: тесты идут за секунду.

## Выпуск версии

Одна команда на чистой `main`:

```sh
yarn release
```

**Что происходит локально.** Прогоняется `yarn check`; версия считается из типов
коммитов с прошлого тега; обновляется `CHANGELOG.md`; всё коммитится как
`chore: release x.y.z`, ставится тег `vX.Y.Z` и пушится. Публикация здесь не
выполняется.

**Что делает CI.** Пуш тега запускает
[`release.yml`](../.github/workflows/release.yml): сверка тега с версией в
манифесте, линт, типы, тесты, сборка, упаковка, проверка содержимого архива,
публикация в npm с провенансом, создание GitHub Release.

**Что проверить после.** Прогон зелёный, и на странице пакета у новой версии
появился значок Provenance со ссылкой на этот прогон.

Руками ни `npm publish`, ни тегов, ни релизов.

### Предрелиз

Уходит под отдельным dist-tag, `latest` не трогает:

```sh
yarn release --preRelease=next
```

### Если прогон упал

Тег уже стоит. Исправить, запушить в `main`, затем передвинуть тег:

```sh
git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z
git tag vX.Y.Z && git push origin vX.Y.Z
```

Повторная публикация уже выложенной версии выпуск не валит — этот случай
обработан отдельно.

## Что проверяется только на устройстве

Тесты покрывают ядро — расчёт вне React. Всё, что происходит между расчётом и
экраном, они не видят:

- отрисовка и наложение строк;
- нативное удержание позиции;
- кадры и плавность;
- прилипание в движении.

Для этого есть восемь стендов в [`example/`](../example), по одному на механику,
и встроенная диагностика: восемь каналов, по одному на механику, с тумблерами
прямо на стендах — см. [debugging.md](debugging.md). Рядом замер,
`useAnchorListPerf`: счётчики пачкой раз в секунду. Как читать отчёт —
[performance.md](performance.md).

Web я объявил неготовым и автоматически не проверяю: удержание позиции опирается
на нативный `maintainVisibleContentPosition`, которого нет в `react-native-web`.
