# Ведение библиотеки

Правка, коммит, выпуск версии. Настройка окружения и работа с PR — в
[CONTRIBUTING.md](../CONTRIBUTING.md).

---

## Цикл одной правки

1. Написать тест, падающий на текущем коде.
2. Проверить, что тест ловит регрессию: вернуть старый код — тест обязан упасть.
3. Починить и прогнать `yarn check` (линт + типы + тесты, тот же набор в CI).
4. Обновить документацию, если менялся публичный API: профильный раздел плюс
   [props.md](props.md).
5. Проверить на устройстве, если правка про отрисовку, скролл или компенсацию
   позиции — [что не покрыто тестами](testing.md#чего-тесты-не-проверяют).

Если причина непонятна — включить канал диагностики
(`setAnchorListDebug("mvcp")`, все каналы в [debugging.md](debugging.md)) или
замер (`useAnchorListPerf`) и снять лог с устройства.

## Коммиты

Формат проверяет `commitlint` на хуке `commit-msg`:

```
тип(область): что изменилось
```

| Тип | Версия | В чендж-логе |
| --- | --- | --- |
| `fix` | патч | **Bug Fixes** |
| `feat` | минор | **Features** |
| `perf` | патч | **Performance Improvements** |
| `revert` | патч | **Reverts** |
| `refactor`, `docs`, `test`, `chore`, `ci`, `build`, `style` | нет | не попадает |

**Заголовок коммита — готовая строка чендж-лога.** Ни тело, ни комментарии туда
не попадают, поэтому заголовок описывает изменение снаружи, а не правку в коде:

```
плохо:  fix: поправил расчёт в sticky-offset
хорошо: fix(sticky): якорь вставал ниже кромки на высоту шапки
```

**Область** — имя из `src/core`: `sticky`, `mvcp`, `edges`, `layout`, `scroll`,
`viewability`, `perf`.

**Одно изменение — один коммит:** каждый `fix` и `feat` даёт ровно одну строку
чендж-лога.

**Ломающее изменение** — отдельной строкой в теле, с указанием, что делать:

```
feat(sticky): наборы прилипания вместо индексов

BREAKING CHANGE: `stickyIndices` заменён на `sticky` — массив наборов
с кромкой, режимом и отступом. Таблица соответствия в docs/sticky.md.
```

Пока мажор нулевой, `BREAKING CHANGE` даёт минор, а не мажор.

**Хуки.** На `pre-commit` идут линт, типы и тесты по изменённым файлам, на
`commit-msg` — проверка формата.

## Выпуск версии

На чистой `main`:

```sh
yarn release
```

**Локально:** прогон `yarn check`, версия из типов коммитов с прошлого тега,
обновление `CHANGELOG.md`, коммит `chore: release x.y.z`, тег `vX.Y.Z`, пуш.
Публикации здесь нет.

**В CI:** пуш тега запускает
[`release.yml`](../.github/workflows/release.yml) — сверка тега с версией в
манифесте, линт, типы, тесты, сборка, упаковка, проверка содержимого архива,
публикация в npm с провенансом, GitHub Release.

**После:** прогон зелёный, у новой версии на странице пакета есть значок
Provenance со ссылкой на этот прогон.

`npm publish`, теги и релизы руками не выполняются.

### Предрелиз

Уходит под отдельным dist-tag, `latest` не трогает:

```sh
yarn release --preRelease=next
```

### Если прогон упал

Тег уже стоит. Исправить, запушить в `main`, передвинуть тег:

```sh
git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z
git tag vX.Y.Z && git push origin vX.Y.Z
```

Повторная публикация уже выложенной версии выпуск не валит.
