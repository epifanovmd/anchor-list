# Удержание видимой позиции

Механика, ради которой список и написан.

## Задача

Список удерживает на месте не «экран», а **конкретную строку**. Всё, что
происходит выше вьюпорта, пользователь видеть не должен.

Два случая:

**Изменились данные.** Подгрузилась страница истории — над видимой частью
появилось 40 сообщений общей высотой в несколько экранов. Без компенсации контент
уезжает вниз ровно на эту высоту.

**Изменились размеры.** Догрузилась картинка в сообщении, которое сейчас выше
экрана. Ячейка выросла на 200 px — и всё, что под ней, съехало.

## Включение

```tsx
<AnchorList
  maintainVisibleContentPosition={{ data: true, size: true }}
  ...
/>
```

| Поле | По умолчанию | Компенсирует |
| --- | --- | --- |
| `data` | `false` | Вставку и удаление элементов |
| `size` | `false` | Изменение размеров уже отрисованных элементов |
| `shouldRestorePosition` | — | Выбор якоря восстановления |

Объект сравнивается по ссылке — мемоизируйте его:

```tsx
const maintainVisibleContentPosition = useMemo(
  () => ({ data: true, size: true }),
  [],
);
```

Обе механики независимы. Ленте, растущей только вниз, не нужна ни одна: они
стоят работы и ничего не дают.

## Как это работает

### Якорь снимается до изменения

Удержание держит на месте конкретную строку, и выбрать её нужно **до**
изменения — по старой раскладке.

Якорем становится первый элемент, целиком лежащий ниже кромки вьюпорта. Строка,
торчащая над кромкой, видна лишь частью и своим размером тянет за собой всё, что
под ней: изменись такая строка — и удержанным окажется её верх, а весь видимый
контент уедет. Такие берутся, только когда других во вьюпорте нет вовсе.

Неизмеренные строки в якоря не годятся: у них позиция оценочная, доводить по ней
нечего.

### Якорей снимается несколько

Первая видимая строка вполне может не пережить то самое изменение, ради которого
якорь и снимался: строка загрузки наверху исчезает ровно тогда, когда приходит
подгруженная порция. Поэтому снимается четыре кандидата подряд, и опорой
становится первый переживший изменение.

### Сдвиг выполняет нативный ScrollView

Это ключевая часть. Компенсация **не** делается программным `scrollTo`.

Списку передан `maintainVisibleContentPosition={{ minIndexForVisible: 0 }}`
нативного `ScrollView`, а первым ребёнком контента лежит распорка нулевого
размера. Нативный код запоминает кадр этой распорки перед mount-транзакцией и
после неё добавляет смещение кадра к `contentOffset`.

Почему именно так:

- **Скролл и раскладка меняются в одной транзакции.** Промежуточного кадра не
  возникает — а программный `scrollTo` пришёл бы отдельным кадром, и это видимый
  прыжок.
- **Жест не обрывается.** Программный скролл посреди жеста гасит и жест, и
  инерцию: пользователь листает, приходит подгрузка — и список останавливается
  под пальцем.

Величина сдвига **накопительная**: нативный слой смотрит на смещение кадра
распорки между транзакциями, поэтому сбросить её в ноль значит сделать обратный
сдвиг на всю накопленную сумму.

### Компенсация применяется целыми точками

iOS отбрасывает смещение кадра меньше 0.5 pt, Android считает его в целых
пикселях. Поэтому сдвиг применяется целыми точками, а остаток меньше точки
копится до следующего прохода.

### Пачка измерений идёт одним проходом

При первом наполнении списка измерения ячеек приходят десятками подряд, каждое
отдельным событием. Пересчёт на каждое из них стоил бы стольких же полных
проходов по раскладке.

Изменения копятся до конца кадра и применяются одним проходом. Заодно это даёт
удержанию единую базу: якорь снимается **до первого** изменения пачки, а
восстанавливается **после последнего**.

## `shouldRestorePosition`

Выбор якоря восстановления. По умолчанию — первый видимый элемент, подходящий по
условиям выше.

```tsx
maintainVisibleContentPosition={{
  data: true,
  size: true,
  // Спиннеры и разделители якорями не годятся: они появляются и исчезают
  // вместе с тем самым изменением, ради которого якорь и снимался.
  shouldRestorePosition: item => item.type === "message",
}}
```

Функция вызывается для каждого кандидата в порядке сверху вниз. Возврат `false`
исключает элемент; кандидат ищется дальше.

## Что видно в замере

Строка `mvcp` встроенного замера ([Производительность](performance.md#замер))
показывает, как механика отработала:

```
  mvcp      12 захватов · 12 восстановлений (данные 8 / размер 4) · сдвиг 340/1204px
            упор 0 · потеряно 0/0px · без якоря 0 · запасной якорь 2 · промах 0 на 0/0px
```

| Величина | Что значит |
| --- | --- |
| `захватов` / `восстановлений` | Сколько раз якорь снимался и применялся |
| `данные` / `размер` | По какой из двух причин |
| `сдвиг` | Средний и максимальный сдвиг, px |
| `упор` | Компенсация уперлась в границу скролла |
| `потеряно` | Сколько пикселей сдвига не удалось применить |
| `без якоря` | Ни один кандидат не подошёл — компенсации не было |
| `запасной якорь` | Первый кандидат не пережил изменение, взят следующий |
| `промах` | Позиция после восстановления разошлась с ожидаемой |

Строки `упор`, `без якоря` и `промах` в норме нулевые. Ненулевые — повод
разбираться, см. [Диагностика](troubleshooting.md).

## Ограничения

**Работает только выше вьюпорта.** Изменения ниже видимой части ничего не
двигают, и компенсировать там нечего.

**Опирается на нативный `maintainVisibleContentPosition`.** `react-native-web`
этого свойства не реализует, поэтому в браузере компенсация не работает вовсе —
см. [Ограничения](limitations.md#web-требует-доработок).

**Нужны стабильные ключи.** Якорь адресуется ключом. Если ключ меняется вместе с
элементом (`${id}:${status}`), якорь после изменения не находится — в замере это
видно как `без якоря`.

**Компенсация упирается в границу скролла.** Если удерживаемая позиция требует
смещения за пределы контента, сдвиг обрезается; в замере это `упор` и `потеряно`.

## Взаимодействие с другими механиками

| Механика | Как связана |
| --- | --- |
| [`maintainScrollAtEnd`](scrolling.md#прилипание-к-концу) | Обратная задача: удержать конец, а не видимую строку. Работают вместе — одна у верха, другая у низа |
| [Подгрузка](pagination.md) | Основной сценарий: `onStartReached` вставляет данные, компенсация не даёт им сдвинуть экран |
| [Стартовая позиция](scrolling.md#стартовая-позиция) | Пока начальный скролл активен, компенсация не мешает: доводка позиции идёт своим чередом |
| [Прилипание](sticky.md) | Не пересекаются: якоря прилипания и якоря компенсации — разные вещи |

## Проверить руками

Стенд «Компенсация позиции» в [`example/`](../example): кнопки вносят изменения
строго выше вьюпорта и печатают смещение скролла до и после. Если компенсация
работает, смещение меняется ровно на высоту изменения, а видимая строка остаётся
на месте.
