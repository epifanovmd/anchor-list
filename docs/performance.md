# Производительность

## Что настраивается

| Проп | По умолчанию | Влияет на |
| --- | --- | --- |
| `drawDistance` | `400` | Сколько строк смонтировано за пределами экрана |
| `scrollThrottleDistance` | `24` | Как часто пересчёт диапазона уходит в JS при скролле |
| `recycleItems` | `false` | Перемонтирование поддерева при смене элемента |
| `getItemType` | — | Точность переработки и оценки размеров |
| `getFixedItemSize` | — | Нужно ли измерять строку вообще |
| `estimatedItemSize` | — | Качество первых кадров |
| `itemsAreEqual` | по ссылке | Пропуск повторных рендеров ячейки |

## Порядок настройки

**1. Задайте `getItemType`.** Почти бесплатно, влияет на две вещи сразу:
переработку контейнеров и точность оценки неизмеренных строк.

**2. Включите `recycleItems`.** Даёт больше всего, если строки однотипные.
Состояние внутри ячеек при этом переводится на `useAnchorListItemState` — см.
[Отрисовка строк](rendering.md#состояние-внутри-ячейки).

**3. Объявите размеры там, где они известны.** `getFixedItemSize` убирает
измерение целиком: ни `onLayout`, ни пересчёта раскладки.

**4. Уточните `estimatedItemSize`.** Влияет только на открытие, но открытие
пользователь и запоминает.

**5. Трогайте `drawDistance` последним** — и только если замер показал, что дело
в нём.

## `drawDistance`

Запас отрисовки за пределами вьюпорта, px. Строки этого запаса смонтированы и
измерены заранее, к моменту, когда до них доходит скролл.

Без запаса элемент монтируется ровно в момент появления на экране и успевает
показаться неизмеренным: сначала оценочной высотой, потом настоящей.

| Значение | Когда |
| --- | --- |
| Меньше 400 | Строки очень тяжёлые, и монтирование дороже редкой пустой полосы |
| 400 (по умолчанию) | Обычный случай |
| 600–800 | Строки лёгкие, а скролл быстрый: списки сообщений, ленты картинок |

Больше 800 обычно бессмысленно: список сам растит запас по скорости.

### Рост по скорости

На броске одного статичного буфера мало: пока событие скролла дойдёт до
пересчёта, а новые строки отрисуются и смонтируются, контент уходит дальше него —
в кадре остаётся пустая полоса.

Поэтому **по ходу движения** буфер растёт со скоростью, и тем сильнее, чем
быстрее скролл. Назад он не растёт: там всё уже отрисовано.

Потолок роста — полтора экрана. Без потолка резкий бросок уводит запас в тысячи
пикселей, а это сотни смонтированных строк: список начнёт тормозить ровно там,
где должен успевать.

### Отказ от запаса на очень быстром скролле

Выше некоторой скорости (около половины экрана в миллисекунду) запас перестаёт
окупаться: смонтировать он успевает меньше, чем контент проходит за тот же
проход. Тогда запас по скорости снимается совсем, и проход становится втрое
дешевле — на экране оказывается то, куда пользователь смотрит сейчас, а не то,
мимо чего он пролетел.

Симметричный `drawDistance` при этом остаётся: между проходом и кадром на экране
лежит коммит, и на скрабе за это время вьюпорт успевает уехать за собственные
границы.

Всем этим список распоряжается сам; настроек тут нет.

## Что список делает сам

**Слияние событий кадра.** Нативный слой шлёт события скролла чаще, чем JS
успевает отрисовать кадр. Лишний проход — это работа, которую никто не увидит,
поэтому события кадра сливаются в один проход.

**Шаг пересчёта.** Пересчёт диапазона уходит в JS шагами по 24 px, а не на каждый
пиксель.

**Пакетирование измерений.** При первом наполнении списка измерения приходят
десятками подряд. Они копятся до конца кадра и применяются одним проходом.

**Адресные сигналы.** Скролл, сдвинувший одну строку, перерисовывает один
контейнер, а не список.

**Фиксация средних размеров.** Среднее по типу набирается по 32 замерам и
замирает. Иначе каждое изменение переставляло бы разом все неизмеренные
строки.

**Отсечение шума измерений.** Изменение измеренной высоты меньше порога — шум
округления экрана, и раскладку оно не двигает.

## Встроенный замер

Отдельная от [диагностики](debugging.md) система и с другим вопросом.
Диагностика объясняет один кадр — из чего сложилось решение механики. Замер
отвечает, сколько всё это стоило за окно и сравнимо ли с прошлым прогоном.

Поэтому здесь нет ни одной величины «на событие»: на быстром скролле поштучный
лог сам становится нагрузкой и меняет то, что измеряет. На событие приходится
сложение числа, а строки собираются раз в секунду.

```tsx
import { anchorListPerf, useAnchorListPerf } from "@epifanovmd/anchor-list";

// Сессия на время жизни экрана.
useAnchorListPerf("chat");

// Или вручную.
anchorListPerf.start("chat");
anchorListPerf.stop();
```

Выключен по умолчанию: каждая точка замера в ядре — одна проверка флага.

Что означает каждая метрика — в каталоге, а не по месту печати:

```ts
anchorListPerf.help();     // все счётчики и величины с подписями
```

Отчёт можно забрать себе — например, чтобы показывать числа на экране, а не
читать их в логе: на устройстве консоли под рукой нет, да и сама печать стоит
кадров, которые же и меряются.

```ts
anchorListPerf.setSink((report, text) => setLines(current => [text, ...current]));

// Накопленное за сессию на любой момент — окно закрывается раз в секунду,
// а экран обновляется чаще.
const snapshot = anchorListPerf.getSnapshot();
```

Свои события можно считать тем же счётчиком:

```tsx
const renderItem = useCallback(({ item }) => {
  anchorListPerf.count("renderItem");

  return <Row item={item} />;
}, []);
```

| Раздел | На что смотреть |
| --- | --- |
| `кадры` | Главная строка. `медиана` — как список идёт обычно; `p95` — где живёт рывок; `длинных` — кадры дольше 24 мс, то есть видимые рывки |
| `скролл` | `лаг` — отставание пересчёта от нативного скролла; `JS` — время в JS на событие |
| `диапазон` | `окно` — сколько элементов в диапазоне; `контейнеров` — сколько смонтировано; `без запаса` — на скольких проходах скорость сняла запас по ходу движения |
| `привязка` | `новых` растёт — контейнеров не хватает; `перепривязок` много — типы не помогают |
| `пустоты` | Должно быть «нет». Ненулевое — в кадре видны незакрытые полосы |
| `стики` | Во что обходится прилипание на каждом проходе |
| `измерения` | `пропущено` — замеры, отсечённые как шум |
| `раскладка` | `задержка` — сколько измерения ждали общего прохода |
| `рендеры` | `на 1000px` — сколько `renderItem` приходится на тысячу пикселей прокрутки |

Строка `mvcp` появляется, когда работает удержание позиции —
см. [Удержание позиции](maintain-position.md#что-видно-в-замере).

Разделы, по которым за окно ничего не происходило, не печатаются: в логе быстрого
скролла важно видеть, что изменилось между итерациями, а не полную таблицу нулей.

При остановке сессии печатается итог за всё время.

### Как читать

| Что видно | Что это значит | Что делать |
| --- | --- | --- |
| `пустоты` ненулевые | Диапазон не успевает за скроллом | Увеличить `drawDistance`; проверить, не тяжелы ли строки |
| `новых` растёт при скролле | Контейнеров не хватает | Обычно следствие сильно разных высот — уточнить `estimatedItemSize` и типы |
| `перепривязок` много | Контейнеры не попадают по типу | Пересмотреть `getItemType` |
| `на 1000px` большое | `renderItem` вызывается чаще, чем нужно | Включить `recycleItems`, задать `itemsAreEqual` |
| `лаг` десятки пикселей | JS не успевает за нативным скроллом | Смотреть, что тяжёлого в кадре помимо списка |
| `длинных` кадров много при спокойном скролле | Дело не в диапазоне | Профилировать содержимое строк |
| `медиана` в норме, а `p95` втрое выше | Список идёт ровно, но регулярно спотыкается | Смотреть, что происходит в эти кадры: `flush`, второй проход компенсации, тяжёлые замеры |
| `медиана` сама по себе высокая | Ровно медленно — дело не в отдельных срывах | Смотреть `диапазон` и `рендеры`: сколько работы на каждый проход |

## Чего замер не покажет

Он меряет **список**, а не строки. Тяжёлый `renderItem` виден косвенно — через
длинные кадры и `на 1000px`, но что именно в нём тяжело, придётся смотреть
профайлером.

## Проверить руками

Стенд «Нагрузка» в [`example/`](../example): тысяча сообщений, подгрузка в обе
стороны, прилипающие даты, измеряемые высоты. Ни настроек, ни экранных счётчиков —
всё, что могло бы повлиять на замер помимо самого списка, из кадра убрано.
