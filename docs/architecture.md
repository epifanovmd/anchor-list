# Архитектура

Как список устроен внутри. Ничего из описанного здесь не экспортируется:
внутренности меняются вместе с реализацией, и опираться на них нельзя. Раздел
нужен, чтобы понимать поведение и читать замер.

## Общая схема

```
┌──────────────────────────────────────────────────────────┐
│  AnchorList (компонент)                                  │
│  тонкая оболочка: монтирует ScrollView, раздаёт контекст  │
└───────────┬──────────────────────────────┬───────────────┘
            │                              │
    ┌───────▼────────┐            ┌────────▼─────────┐
    │  ListRuntime   │  сигналы   │   ListStore      │
    │  расчёт вне    ├───────────►│  адресные        │
    │  React         │            │  подписки        │
    └───────┬────────┘            └────────┬─────────┘
            │                              │
   ┌────────▼─────────┐          ┌─────────▼──────────┐
   │  ListMetrics     │          │ ListItemContainer  │
   │  ключи, размеры, │          │ по одному на       │
   │  позиции         │          │ видимую строку     │
   └──────────────────┘          └────────────────────┘
```

Главная идея: **диапазон отрисовки, позиции и привязка контейнеров считаются вне
React**. В дерево уходят только адресные сигналы, поэтому скролл и измерения не
перерисовывают список целиком — перерисовывается только затронутый контейнер.

## Слои

### Компонент

`AnchorList` монтирует `Animated.ScrollView`, отдаёт ядру размеры и события и
раздаёт дереву контекст. Собственной логики раскладки в нём нет.

Внутри `ScrollView` в порядке сверху вниз:

| Узел | Зачем |
| --- | --- |
| Якорь компенсации | Первый ребёнок контента, нулевой размер — за ним следит нативное удержание позиции |
| Шапка | `ListHeaderComponent`, измеряется |
| Слой контейнеров | Задаёт высоту контента; контейнеры внутри позиционированы абсолютно. Короткий контент прижимает к концу трансформ слоя — в высоту он не входит |
| Распорка у конца | `anchoredEndSpace` |
| Подвал | `ListFooterComponent`, измеряется |
| Распорка нижнего отступа | Высота `insetEnd`; ниже подвала — панель ввода перекрывает и его |

Снаружи `ScrollView`, но внутри обёртки — слой прилипших копий: он живёт в
координатах вьюпорта и потому не едет вместе с контентом.

### Расчётное ядро

`ListRuntime` — координатор. Само оно почти ничего не делает: держит смещение,
размер вьюпорта и текущий диапазон, а содержательную работу делают отдельные
части. Здесь живёт только то, что связывает их между собой, — **порядок вызовов,
от которого зависит, увидит пользователь прыжок или нет**.

Ключевые связки:

- смена пропов снимает якорь компенсации **до** смены данных и восстанавливает
  позицию **после**: якорь обязан помнить раскладку до изменения;
- приём измерения копит изменения до конца кадра, но якорь снимает **сразу** —
  база компенсации должна относиться к состоянию до первого изменения пачки;
- восстановление позиции считает раскладку дважды и в одном синхронном проходе с
  записью позиций;
- обработка скролла отбрасывает события, отправленные до применения сдвига,
  считает проход по живому смещению UI-потока и сливает события кадра в один
  проход.

### Хранилище сигналов

`ListStore` — именованные значения с адресной подпиской.

Расчёт идёт вне React на каждом кадре скролла и на каждом измерении ячейки.
Гонять это через состояние компонентов значит перерисовывать список целиком там,
где на экране сместилась одна строка.

Значения читаются синхронно из расчётного цикла и подписываются точечно из
компонентов. Запись без изменения значения никого не будит — сравнение по ссылке
отсекает повторы, которых при пересчёте раскладки большинство.

Сигналы бывают двух видов:

- **общие** — состояние всего списка (`totalSize`, `isNearEnd`,
  `firstVisibleIndex`, …). Это они выходят наружу через `sharedValues` и `state`;
- **адресные, по одному набору на контейнер** — `containerPosition3`,
  `containerItemKey3`, `containerSticky3` и так далее. Адресность здесь и есть
  весь смысл: смещение одного контейнера при скролле не должно перерисовывать
  остальные.

### Метрики

`ListMetrics` — всё про размеры и позиции:

| Часть | За что отвечает |
| --- | --- |
| Соответствие ключ ↔ индекс | Обратное преобразование за константу; подсказывает, с какого места поехала раскладка |
| Размеры элементов | Объявленные, измеренные, оценочные; пометка «ещё не измерен» |
| Средние по типам | Оценка неизмеренных строк; фиксируется после 32 замеров |
| Префиксные суммы позиций | Позиция элемента без обхода всего списка |

Всё адресуется **ключом**, а не индексом: размеры, привязки контейнеров и якоря
удержания позиции обязаны пережить вставку, удаление и перестановку данных.

## Контейнеры

Контейнер — единица монтирования. Строк в данных тысячи, а смонтированных
контейнеров — по числу тех, что помещаются в диапазон отрисовки.

```
данные:      [0][1][2] ... [847][848][849][850] ... [9999]
                            └──── диапазон ────┘
контейнеры:                  #3   #7   #1   #4
```

Контейнер переживает смену элемента: ядро меняет его сигналы, и перерисовывается
только он один. Всё, что он знает о своём содержимом, приходит адресными
сигналами.

### Пул

`ContainerPool` раздаёт контейнеры под запрошенные строки. Свободный контейнер
**того же типа** предпочтительнее любого другого: попадание по типу означает
совпадающую структуру поддерева, и React меняет пропы вместо перемонтирования.

Прилипающие контейнеры живут отдельно: их держат смонтированными и за пределами
видимого диапазона, поэтому под обычные элементы они не уходят. У прилипающей и
обычной строки разная React/Reanimated-структура, и между этими ролями
контейнеры не переиспользуются.

Контейнер без привязки не размонтируется — он ждёт следующего элемента, поэтому
его просто уводят туда, куда скролл не доходит.

## Проход раскладки

Один проход при скролле:

```
событие скролла (UI-поток, worklet)
  └─ запись scrollOffset
  └─ шагами по 24px → JS
       └─ ListRuntime.setScroll
            ├─ слияние событий кадра в один проход
            ├─ расчёт скорости
            ├─ computeVisibleRange       — какие строки нужны
            ├─ collectContainerRequests  — какие из них не отрисованы
            ├─ ContainerPool.allocate    — раздача контейнеров
            ├─ запись позиций в сигналы  — перерисуются только сдвинувшиеся
            ├─ EdgeThresholds.check      — пороги подгрузки
            ├─ StickyPublisher           — активные якоря
            └─ ViewabilityTracker        — если есть подписчики
```

Проход при измерении ячейки:

```
onLayout ячейки
  └─ фильтр шума (субпиксельная разница игнорируется)
  └─ ListRuntime.setItemSize
       ├─ якорь компенсации снимается сразу
       └─ LayoutScheduler — копит до конца кадра
            └─ один проход раскладки на всю пачку
                 └─ восстановление позиции по якорю
```

## Компенсация позиции

Сам сдвиг выполняет нативный `ScrollView`, а не JS.

Ему передан `maintainVisibleContentPosition={{ minIndexForVisible: 0 }}`, а первым
ребёнком контента лежит распорка нулевого размера. Нативный код запоминает её
кадр перед mount-транзакцией и после неё добавляет смещение кадра к
`contentOffset`.

Это единственный способ поменять смещение скролла в той же транзакции, что и
раскладку: программный `scrollTo` пришёл бы отдельным кадром (видимый прыжок) и
вдобавок оборвал бы жест и инерцию.

Позиция распорки **накопительная**: нативный слой смотрит на смещение её кадра
между транзакциями, поэтому сбросить её в ноль значит сделать обратный сдвиг на
всю накопленную сумму. Сама распорка вынесена далеко за пределы контента, чтобы
попадать под условие `minIndexForVisible` при любом смещении.

## Прилипание

Смещение якоря и предикат «стоит у кромки» — worklet-функции: считаются на
UI-потоке в такт скроллу.

Предел смещения (докуда якорь может сдвинуться, прежде чем его вытолкнет
следующий) считается в JS для каждого якоря и зависит только от геометрии
соседей, но **не** от позиции скролла: иначе значение менялось бы на каждом кадре
и дёргало worklet.

Три состояния и слой копий разобраны в [Прилипание](sticky.md#слой-прилипших-копий).

## Структура исходников

```
src/
  index.ts            публичный экспорт
  types.ts            публичные типы

  components/         React-слой
    AnchorList.tsx      компонент
    ListContainers      слой контейнеров
    ListItemContainer   один контейнер
    ListItemContent     содержимое ячейки и её измерение
    ListStickyFrame     обёртка прилипающей строки
    ListStickyOverlay   слой прилипших копий
    ListStickyPin       копия одной кромки
    ListScrollAdjust    якорь компенсации
    ListAnchoredEndSpace распорка у конца
    ListInsetEndSpace   распорка нижнего отступа

  core/               расчёт вне React
    runtime/            координатор и приведение пропов
    layout/             диапазон, привязка контейнеров, распорки, пакетирование
    scroll/             стартовая позиция, программный скролл, нижний отступ, скорость
    mvcp/               удержание видимой позиции
    sticky/             якоря, пределы, смещения
    edges/              пороги кромок
    viewability/        видимость элементов
    data/               разбор данных в ключи и типы

  model/              состояние
    list-store          хранилище сигналов
    list-signals        имена и начальные значения
    list-state          доступ снаружи дерева
    list-context        контекст дерева
    container-pool      пул контейнеров
    metrics/            ключи, размеры, позиции, средние

  hooks/              мосты в React и Reanimated
  perf/               замер производительности
```

## Что не делается

**Нет пересчёта на каждое событие скролла.** События кадра сливаются, пересчёт
идёт шагами по 24 px.

**Нет полного перебора данных на проходе.** Диапазон ищется по префиксным суммам,
обход идёт только по нему.

**Нет прохода по всем контейнерам при сдвиге.** Позиции пишутся адресно, и
перерисовываются только те, у кого позиция изменилась.

**Нет рендера на скролл.** Смещение живёт на UI-потоке; в JS уходит только шаг
пересчёта.
